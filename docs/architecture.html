Data Flow — Filter → Render

1
User adjusts FilterBar
Time Period, Warehouse, Category, or Order Status — bound via v-model to shared refs in useFilters.js.
2
Shared filter state updates
Module-level refs (singleton composable) mean every view reads the same filter selection — no store library needed.
3
View requests data
Active view calls getCurrentFilters() then a function in api.js, e.g. getOrders(filters).
4
Axios GET with query params
Request sent to FastAPI, e.g. /api/orders?warehouse=Tokyo&status=shipped.
5
In-memory filtering
apply_filters() and filter_by_month() in main.py list-comprehend over the module-level Python lists from mock_data.py.
6
Pydantic validation
Result coerced against the route's response_model before serialization to JSON.
7
Raw data lands in refs
Response stored in the view's local raw refs, e.g. allOrders, inventoryItems.
8
Computed properties render
Templates read derived computed() values — totals, charts, tables — that stay in sync with the raw refs.

Known Gaps & Inconsistencies

  • Dead API calls in the client: api.js exports getTasks, createTask, deleteTask, toggleTask, createPurchaseOrder, and getPurchaseOrderByBacklogItem, targeting /api/tasks* and /api/purchase-orders* — none of these routes exist in main.py. Task loading in App.vue silently 404s and falls back to mock data from useAuth.
  • Unrouted view: client/src/views/Backlog.vue exists but has no entry in the router (main.js) and no nav link in App.vue — it's unreachable from the UI.
  • Missing test file: tests/README.md and tests/TEST_SUMMARY.md both document a test_orders.py (15 tests) that does not exist in tests/backend/ — Orders endpoint coverage is currently missing despite being documented.
  • Duplicate MCP config: root .mcp.json pins @playwright/mcp@0.0.37, while .claude/mcp-config.json uses @playwright/mcp@latest — the two configs can drift out of sync.
